## 已确定的问题

1. **每次 LLM 调用上限为 180 秒**，不是整个项目仅能运行 180 秒。
   第 1 个复扫、第 2 和第 3 个扫描的终止事件均为 `context deadline exceeded`。
   LLM 客户端的重试共用同一个调用 context，deadline 耗尽后重试也无剩余时间。
2. **单个上下文任务失败会取消同项目全部并发任务**。
   `contextaudit/runner.go` 将 worker 错误写入 errCh 后调用 cancel，最后返回错误；
   没有把这一失败单独保存为可续跑的任务结果。
3. **工具参数格式不兼容**。第 3 个项目候选发现阶段有 12 次模型调用将参数
   放在 tool 同级，缺少执行器要求的 args。对应 12 次工具错误均为
   `unexpected end of JSON input`，不是 Java 项目文件解析错误。
4. **原生复核未预留保存结论轮次**。该问题已按用户上一条授权修复，且真实第 1 个
   项目补跑已保存全部 5 条判定；后续失败来自复扫超时，不能把两类问题混为一谈。

另有无效正则、只读 Bash 检查拒绝带重定向命令等可恢复工具错误；它们不是已观察到的
终止错误，不应为了绕过错误而开放写权限。

## 仍不确定的部分

没有看到 401、429 或额度不足的终止错误，不能据此保证账号未受任何内部排队影响。
现有扫描客户端未记录 finish_reason、推理字段和失败请求耗时/usage，无法判定
慢调用是模型推理、中转排队还是网络。日志中 Kimi 标记式工具调用受上下文解析器支持，
不能将所有非裸 JSON 响应都算作格式失败。

单个任务失败会损失同项目进展，与故障传播策略有关；并不证明提高并发或更换模型
一定能解决。仅把 timeout 调大也不能解决格式兼容及故障隔离问题。
